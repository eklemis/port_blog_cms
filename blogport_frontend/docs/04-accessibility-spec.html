Sixth paper · the one with numbers in it

Accessibility Specification

Every other paper in this set describes intent. This one measures. The palette was audited pair by pair against WCAG 2.2 AA, six tokens failed, and all six were changed in the Figma variables before this document was written — so the ratios below describe the file you have, not a target to aim at.

The design system moved. If you already pulled theme.css, replace it. Six colour values changed and one token is new.

01

The standard, and what it binds

The target is WCAG 2.2 Level AA. Not AAA — AAA would force a 7:1 text ratio that this palette cannot carry without abandoning the amber accent, and would ban the justified prose the public post template uses. AA is the level that regulation actually references.

It binds the tokens, not the screens

Contrast is a property of a colour pair, and every colour in this product resolves through the Theme variable collection. Auditing 17 variables across 2 modes covers all 210 screens. Auditing screens would not have covered the ones nobody has drawn yet.

Dark mode is audited separately, not assumed

A palette that passes in light routinely fails in dark, because the dark surfaces sit close together — #2f3133, #3a3c3e and #434547 are within 20 points of each other. Four of the six failures found were dark-only.

Three grounds, not one

Text lands on bg, on surface, and on surface-2. A token is only compliant if it clears the bar on the worst of the three. Checking against one ground is how most palettes pass an audit and still fail in use.

What was checked

62 foreground/ground pairs: 9 text tokens × 3 grounds × 2 modes, plus button text on the accent fill and the control boundary against each ground. 21 pairs failed on the first pass. All 21 now clear their threshold, by changing six token values and adding one.

What is exempt, and why arch/line still measures 1.17:1

arch/line is a hairline divider — the rule under a table header, the edge of a card. WCAG 1.4.11 applies to boundaries that are needed to identify a control. A divider identifies nothing, so it is exempt, and darkening every rule in the product to satisfy a checker would make the interface louder for no one's benefit.

The moment a border is the only thing telling you where an input begins, the exemption stops applying. That is why arch/line-control exists.

04

Colour is never the only signal

1.4.1 is the criterion most often failed by a design that passes contrast. Roughly one man in twelve cannot separate the red and green in this palette; every one of them still has to tell a failed upload from a finished one.

WhereColour saysWhat else says it
StatusPillFive semantic huesA word — Live Processing Failed — plus a filled dot. The word is the signal; the hue is reinforcement.
Field errorRed border and red textThe help line is replaced by the error sentence and wired with aria-describedby. A red ring with unchanged text is not an error state.
MediaTileAmber / red / grey washA state pill and a distinct action pair — Retry · Remove for failed, Restore · Purge for archived.
ATS barsBar length and hueA numeral and a named band. A null relevance renders one bar with a stated reason, never a zero bar.
SaveIndicatorGreen tick on savedThe words Saving…, Saved 10:42, Unsaved changes. The timestamp is the proof.
Diff in AI suggestionsAdded green, removed redStrikethrough on removal, underline on addition — so the change survives a greyscale print and a colour-blind reader.
05

Focus

One ring, everywhere, on everything focusable. Never removed without a replacement that is at least as visible — outline:none with nothing after it is a defect, not a style.

Publish Preview Unfocused, for comparison

outline: 2px solid var(--color-arch-accent-ink); outline-offset: 2px; — offset so the ring reads against both the control and the ground behind it. On the amber primary it sits outside the fill rather than on it.

Order follows the document

Tab order is DOM order. No positive tabindex anywhere in this product. Where the visual order and the DOM order disagree — the editor rail sits right of the canvas but is reached after it — the DOM is what the design intends.

Dialogs trap, then return

ConfirmDialog and the Export modal move focus to the first control on open, hold it inside while open, and return it to the element that opened them on close. ConfirmDialog opens on Cancel, never on the destructive action.

Skip the shell

A skip link to #main is the first focusable element on every page. The console sidebar is 8 links before content on desktop, and the tablet rail collapses those to icons without changing how many stops they cost.

Async never steals focus

A toast, a completed save, a finished stream — none of them move focus. The only movements are ones the person initiated. An undoable toast is reachable by Tab and its dwell timer pauses while it holds focus or hover.

06

Keyboard

The full map. Everything achievable with a pointer is achievable here; there is no pointer-only path anywhere in the product.

KeyContextDoes
Tab / Shift+TabEverywhereMove through focusable elements in DOM order.
EnterButton, link, table rowActivate. In ConfirmDialog it never confirms — the destructive action needs a deliberate click or Space on the armed button.
SpaceButton, checkboxActivate / toggle. Never scrolls when a control has focus.
EscDialog, Combobox, bottom sheetClose and restore focus. On a Combobox it closes the list and keeps the typed value.
↑ ↓Combobox listMove the active option. Does not change the value until Enter.
EnterCombobox, no matchCreate the topic being typed, when creation is offered. The offer is visible before the key is pressed.
Cmd/Ctrl+SEditorsForce a save now. Autosave already runs; this exists because people press it regardless.
Cmd/Ctrl+EnterPost editorOpen the publish dialog. Never publishes directly.
Cmd/Ctrl+ZAfter an applied AI suggestionRevert it. Suggestions stay undoable for the session.

The editor is a text area, not a canvas

Markdown is edited as plain text. That is an accessibility decision as much as a product one: a rich-text canvas would need a full custom keyboard model and would fight the screen reader's own text navigation. Here, arrow keys, selection and dictation all work because nothing was rebuilt.

07

Target size and pointer

WCAG 2.2 added target size at AA with a 24×24 CSS pixel minimum. The platform guidance most people quote — 44×44 — is stricter than the standard, and worth meeting where it costs nothing.

ControlDrawn2.2 AA · 24pxPlatform · 44px
Button, mobile and tablet36px tall — 40 instances across the mobile setPassesUnder — raise to 44 in the build
Button, desktop36px tall, pointer inputPassesNot required — 44 is a touch guideline
Sidebar nav row, tablet rail40 × 40PassesUnder — pad the rail to 44 if tablets matter
Table row actionInline text link inside a 44px rowPasses — the row is the targetPasses
Inline link in a sentenceText only — "Forgot password?" measured ~14px tallFails unless paddedFails unless padded
Text input20px input inside a 44px padded boxFails if only the input is clickablePasses when the box is the target
Toast close24 × 24 icon, 40 × 40 hit areaPassesUnder

Two rules this table did not have, found while building the first screen

An inline link inside a sentence needs its hit area padded to 24px. The text is ~14px tall, and "Forgot password?" sitting in running copy is a target no rule here had sized. Padding is invisible; it costs the layout nothing.

A control's target is its padded box, not the glyph inside it. A 20px text input centred in a 44px box passes only if the whole box is clickable. If the border is the only hit area, the control fails at every width and the table above would still say it passes.

Both were caught in implementation rather than here, which is the tell: this table sized components and missed the targets that are made of text. When you add a row, ask what the person actually has to hit, not what the component is called.

Recommendation, not a defect: bump the mobile Button height from 36 to 44 and pad the tablet rail rows. Nothing here fails the standard — it is the difference between compliant and comfortable, and it is a token change rather than a redesign.

Pointer rules that come free

No hover-only affordance anywhere: every action revealed on hover is also present on focus and permanently visible on touch. No drag-only interaction — media reordering offers move up / move down alongside the drag. No gesture the product invents.

What each of the ten components must expose. Prefer the native element every time — the ARIA column is for what the native element cannot say on its own.

09

Live regions and asynchronous work

This product does a lot without being asked: it autosaves, it streams model output, it processes uploads. Every one of those is invisible to a screen reader unless it is announced — and unbearable if it is announced too often.

Announce the settled state, not the transition

The save indicator announces Saved and Unsaved changes. It does not announce Saving…, which would fire on every pause in typing and make the editor unusable with a screen reader running.

Streaming text is not a live region

Token-by-token model output inside aria-live produces a stream of interruptions. The streaming area is aria-busy="true" while it runs; when it settles, one polite announcement says the draft is ready and how long it is. The text itself is then read on demand.

Assertive is reserved for loss

Only two things interrupt: a save that failed, and an action that lost data. Everything else — success, completion, upload finished — is polite. An assertive success toast is the fastest way to make someone turn the screen reader off.

Partial failure keeps what arrived

When a stream errors mid-flight the text on screen stays, an assertive message says where it stopped, and both Try again and Keep this are focusable. Clearing the region would discard work the person watched being produced.

AI_DISABLED is a configuration, not an error

When the AI features are switched off the companion surfaces are muted and explanatory — never red, never an alert, no retry. Announcing a deliberate configuration as a failure teaches people to ignore real failures.

Motion

There is very little of it, which makes the rule easy: honour the preference, and never make motion carry meaning.

MotionDefaultUnder reduced motion
Toast enter / leave120ms fade and 4px riseAppears and disappears, no transform. Dwell time unchanged.
Dialog open100ms scrim fadeScrim appears instantly. Focus behaviour identical.
Skeleton shimmerSweep on loading rowsStatic blocks. Loading is still announced politely.
Streaming caretBlinking blockSolid, no blink. Blink rate never exceeds 3Hz in either case.
Button loading spinnerRotates, suppressed under 400msStatic glyph plus the busy state. The 400ms floor still applies.

@media (prefers-reduced-motion: reduce) is a global rule in the stylesheet, not a per-component opt-in. Nothing auto-advances, nothing auto-plays, and no animation loops more than five seconds without user control.

11

Errors, identified and suggested

3.3.1 asks that the error be identified in text. 3.3.3 asks that a correction be suggested when one is known. The second is the one that is usually skipped.

FailureIdentified asSuggested
Slug already taken"That slug is already in use."Offers the next free variant as a one-click fix.
Password too shortNames the minimum, on blur, never mid-typing.The requirement is stated before the field is touched, so the error is a reminder rather than news.
Upload rejectedNames the limit and the actual size — "14MB, limit is 10MB".Keeps the file selected so a replacement is one action, not a restart.
Sign-in failedOne message for both wrong address and wrong password.Deliberately no suggestion — distinguishing the two would confirm which addresses have accounts.
Session expired mid-editAssertive. Says the draft is held locally.Sign in again in place; the editor is restored, not reloaded.

Errors appear on blur, never on keystroke

A field that turns red while you are still typing in it is reporting a problem you have not finished causing. Validation fires on blur, and once a field is showing an error it revalidates live so the error clears as soon as it is fixed.

12

Language

The product ships in English and Indonesian, and the two mix on a single page more often than the switcher suggests.

The page declares its language

<html lang> follows the interface locale and changes when the switcher changes. Without it a screen reader pronounces Indonesian with English phonetics.

So does content that disagrees with it

A CV written in Indonesian inside an English interface takes lang="id" on its own container. This is 3.1.2, and it is the criterion this product is most likely to fail — a bilingual portfolio is the normal case here, not the exception.

The switcher is a control, not a flag

It is a labelled button reading EN / ID with an accessible name of "Language". No flag icons — a flag names a country, not a language, and Indonesian is not a country.

Nothing is translated by layout

Both languages are left-to-right, so no mirroring is required. Copy length differs by roughly a fifth, which is why no button in the design system is sized to its English label.

Images and media

Alt text is a product feature here, not a template attribute — the media library has a field for it, an empty state that nags, and since backend round one, the ability to change it.

CaseRule
Post coverAlt required before publish. The publish dialog names the missing alt as a blocking item, not a warning.
Body image![alt](media:id) — the alt travels in the Markdown and is resolved at render. An empty alt is allowed only when the image is decorative and the author has said so.
Decorativealt="" and role="presentation". Never omit the attribute — a missing alt makes a screen reader read the filename.
AvatarAlt is the person's name when the image is the only representation, empty when the name sits beside it. Both appear in this design; the name is beside it in the header, so that one is empty.
Project screenshotAlt describes what the screenshot shows, not that it is a screenshot. "Kafka topic lag over a week" beats "Screenshot of dashboard".
Charts in the CVThe ATS bars are not images. They are text and DOM, so they need no alt and survive zoom.

The alt-text empty state earns its place

No alt text — add one renders in status/danger on the media tile, and the media list can be filtered to exactly those. That is the difference between a product that permits accessible content and one that produces it.

14

Zoom and reflow

1.4.10 asks that content reflow to 320 CSS pixels without a second scrollbar. 1.4.4 asks that text scale to 200% without loss. The design now has drawn frames at three widths, so neither is guesswork.

WidthStatusBehaviour
< 768px70 frames390 × 844, light and dark. Tab bar, cards, bottom sheet. Reflows to 320 without horizontal scroll.
768 – 1023px70 frames834 × 1112, light and dark. Sidebar collapses to a 64px icon rail; tables keep three load-bearing columns; the editor rail stays a rail.
≥ 1024px70 frames1180 wide, light and dark.

Tables scroll in their own container

Every table sits in an overflow-x:auto wrapper. The page body never scrolls sideways — that is the specific failure 1.4.10 is written to prevent.

Text scales because nothing is pinned to pixels

Type is set in rem, containers in ch and percentages. At 200% the console becomes the tablet layout, which is drawn — not an untested reflow.

No width gets a wall

Nothing in this product answers a viewport with "please use a larger screen". It applied when fifteen screens were undrawn; it still applies now that none are.

Zoom does not hide controls

Actions that collapse into an overflow menu at narrow widths stay reachable and keep their accessible names. Collapsing is a layout change, never a capability change.

15

What to test, and what this document cannot promise

Contrast is provable from the tokens and is now proved. Everything else in this document is a specification that the build either meets or does not — automated tooling will catch perhaps a third of it.

CheckHowCatches
Axe / Lighthouse in CIPer route, both themesMissing labels, bad contrast on anything hard-coded outside the tokens, duplicate ids, missing lang.
Keyboard-only passUnplug the mouse, walk §06Focus traps, lost focus after dialogs, hover-only actions. Nothing automated finds these.
Screen reader spot-checkVoiceOver/Safari and NVDA/Firefox on: post editor, media library, tracker, publish dialogOver-announcement from live regions — the most likely defect in this product, and invisible to every linter.
200% zoomDesktop browser, both themesClipped controls, horizontal scroll, text that stops reflowing.
Forced coloursWindows high contrastAnything that carries meaning in a background image or a border colour alone.

Three things this document does not cover

The rendered PDF. Export produces a document, and PDF accessibility — tagging, reading order, embedded language — is a separate standard. A CV exported from here is currently an untagged PDF. That is a known gap, not an oversight.

Model output. The companion writes prose. Nothing guarantees that prose is readable at a given grade level, and the product does not claim it is. What the product does guarantee is that the suggestion is always visible as text before it is applied.

Author-supplied content. A published post's heading order, link text and image alt are the author's. The editor prompts for alt and blocks publish without cover alt; it does not police heading structure, and should not silently rewrite what someone wrote.

If you change a colour, re-run the audit

The ledger in §02 is a snapshot of 17 variables. Any new token, any nudge to an existing one, and the pairs have to be recomputed against all three grounds in both modes. The failure mode is not dramatic — it is one status colour drifting under 4.5 and nobody noticing for a year.
