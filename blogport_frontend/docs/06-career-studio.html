Career Studio Design Paper

A writing companion for CVs and a tracker for the applications they go into — plus the two cross-cutting changes they force: a light theme the product has never had, and a language setting that turns out to be two settings, not one. The backend surface it needs is filed as R15–R21 in Blogport API Round Two.

Light and dark

The product has been dark-only since it started. Adding light is not "invert the greys" — the accent breaks, the inputs disappear, and the status scale stops being legible. Here is the pair that works.

The accent has two roles, and light mode is where that stops being optional

#f4a43d on white is roughly 2.1:1 — it fails WCAG AA for text by a wide margin. On charcoal the same amber is comfortable, which is why the problem has never surfaced. So the token splits in two: --arch-accent stays the fill for buttons and active bars (with --arch-accent-on as the dark text that sits on it), and --arch-accent-ink is accent-coloured text — links, active nav, focus rings — which resolves to a deep ochre on light and stays bright amber on dark.

Practical rule for the developer: a link is never text-arch-accent. It is always text-arch-accent-ink. The fill token on text is the single most likely way this theme gets shipped broken.

Ground rules

The light ground is cool, not cream

The charcoal #2f3133 leans very slightly blue, so its counterpart does too. A warm cream ground under a warm amber accent leaves nothing to contrast against, and lands squarely on the most generic light palette going.

Three states, not two

Light, Dark, and System — defaulting to System. A two-state toggle silently overrides the OS preference the first time it is touched, with no way back. Persist the choice per browser; sync to the account only once the backend has a field for it.

Stamp before paint

A synchronous script in app.html reads the stored choice and prefers-color-scheme, then sets the class on <html> before the first stylesheet. Skip it and every cold load flashes white at dark-mode users. It is eight lines and it is in theme.css.

Surfaces lift on light, recede on dark

On light, a card is white on grey with a hairline shadow. On dark, it is lighter grey on charcoal with no shadow at all — shadows on dark grounds read as smudges. Same component, different elevation language; --shadow resolves to none in dark.

Inputs get a surface

The old login form used bg-transparent inputs. On a light card that is an invisible field with a hairline. Inputs are bg-arch-surface in both themes.

Status darkens, it doesn't invert

Each of the five status values gets a light-mode variant chosen for legibility on a pale ground — #8fbf9a becomes #2e6b45, not a lighter green. Meaning is preserved; luminance flips.

02

Language is two settings

"Language selection" reads like one dropdown. For this product it is two, they are independent, and conflating them is the single most likely design error in this paper.

UI languageContent language
ControlsNavigation, labels, buttons, errors, dates, number formatsWhat the AI writes, and what a CV or cover letter is written in
ScopeOne per personOne per document — per CV, per cover letter
Lives onuser.localecv.language, cover_letter.language
Chosen inSettings, plus a compact switcher on login and public pagesThe document header, beside the title — visible while writing
Changing itInstant, no data effectDoes not retranslate. It tells the AI which language to work in from here.

Why they have to be separate

The obvious real case: someone who reads the interface most comfortably in Indonesian, applying to an international company, writing an English CV. A single setting forces them to operate the whole app in a second language to get an English document — or worse, silently generates a CV in the wrong language for the employer. Launch with English and Indonesian, and build the switcher so a third locale is a file rather than a refactor.

The AI needs the content language explicitly. Inferring it from the CV's existing text breaks on a half-written document and on CVs that legitimately mix languages — a technical skills section in English inside an Indonesian CV is normal, not a mistake to correct.

Where the switcher is actually drawn — counted, September 18

"Settings, plus a compact switcher on login and public pages" is the rule above. The frames carry it in 34 places: every auth screen at all three widths (sign in, create account, forgot, reset, verification gate), and every public screen at desktop and tablet. The one exception is mobile public, where the nav folds behind ☰ and the pill goes with it.

So the switcher belongs to two layouts, not one — the auth shell as well as the public shell.

It is now buildable. R20 shipped while this callout still said to wait: locale is on UserProfileResponse and writable through PUT /api/users/me. The auth shell has no session to write to, so there the switcher sets the local preference only and the account picks it up at sign-in — the same three-state rule as the theme in §01, and the same reason it is stored per browser first.

What this costs elsewhere

Dates and numbers are not strings

Every date in the tracker and every count in the console goes through Intl.DateTimeFormat / Intl.NumberFormat with the active locale. Hand-formatted DD/MM/YYYY is a bug the moment a second locale exists.

Error copy is content, not code

The error-code table in the Console Blueprint maps codes to English sentences. That mapping becomes a message catalogue keyed by code — which is exactly why the blueprint insisted the raw code never reaches the screen. That rule now pays for itself.

Decide about RTL now, not later

Neither launch locale needs it. But writing margin-inline-start instead of margin-left from the start costs nothing today and saves a full layout audit if Arabic ever appears. Use logical properties; don't build an RTL mode yet.

Public pages need a locale in the URL

A shared link has no session to read a preference from. If public pages are ever localised, the locale belongs in the path — and that is a routing decision worth making before the routes exist, not after they are indexed.

03

The companion

Not a chatbot in a corner. The companion appears where the writing happens, acts on a selection, and always proposes rather than replaces.

The rule everything else follows: it never invents a fact

A CV is a claim a person makes to an employer, and a cover letter is signed by them. If the model writes "reduced latency by 40%" because that is the shape of a strong bullet, the product has authored a lie the user will be asked about in an interview.

The companion may rephrase what the user wrote. It may never introduce a metric, employer, date, title, or credential the user did not supply. Where a bullet would be stronger with a number, it asks — "Do you know roughly how much this reduced latency?" — and leaves a blank the user fills. That single constraint is what separates this from a plausible-résumé generator, and it is a UI shape, not a prompt instruction: the ask renders as an input, not as prose.

Where it appears

SurfaceActs onWhat it offers
Inline, on selectionA highlighted bullet or sentenceTighten · Strengthen the verb · Add a metric (asks) · Match to this job

Interaction laws

Propose, never overwrite

Every suggestion lands as a reviewable change — side-by-side for a bullet, a diff for a tailoring pass. Accept per change. There is no "rewrite my CV" button that silently replaces a person's own words, because a wholesale rewrite is unreviewable in practice.

Stream, and stay interruptible

A cover letter is a long generation. Stream it, keep a visible Stop, and let the user start editing the part that has landed while the rest arrives. A modal spinner over a 20-second generation is the difference between a tool and a wait.

Undo is not optional

Every applied suggestion is one ⌘Z away, and the editor keeps a pre-tailoring snapshot for the whole session. People accept a change, read it again, and change their mind — that is the normal path, not an error case.

Say what it read

When a suggestion draws on the job description, the UI says which requirement it came from. "Matches: 3+ years distributed systems" turns an opaque instruction into a judgement the user can disagree with.

Failure is a state, not a modal

Rate limits, refusals and timeouts land in the panel where the suggestion would have been, with a Retry. The user's document is never blocked on the model being available.

Off is a real setting

Someone who wants a plain CV editor gets one. The companion collapses to a single icon and stops making calls. This also matters for cost: not every keystroke needs a model.

The tracker

One row per application. The table is the primary view because this is a list people scan for "what needs chasing" — a kanban board looks better in a screenshot and reads worse at forty applications.

Status pipeline

Six live states and three terminal ones. Statuses reuse the product's existing five status colours — no new colour vocabulary for this feature.

draft applied screening interview final offer accepted rejected withdrawn no reply

"No reply" is its own outcome, and it is the most common one

Folding silence into rejected destroys the most useful signal in the whole dataset. A rejection after three interviews and a job that never replied are different events with different lessons, and lumping them together makes any later pattern-finding worthless. Auto-suggest the transition after 21 days — never apply it silently, because sometimes people do reply on day 30.

The CV column stores a snapshot, not a pointer

If the tracker links to CV #3 and the user keeps editing CV #3, then in two months every past application claims to have used a document that did not exist when they applied. At interview time, the one question this product must answer — what exactly did they read? — becomes unanswerable.

Freeze a copy at the moment the status leaves draft. The row shows "CV — Senior Backend, as sent 14 Aug" and opens read-only, with an explicit "Start a new version from this" action.

05

Five journeys

Continuing the Console Blueprint's numbering. Same conventions: ordered steps, and failure branches that name a recovery.

J11

Capture a job

An advert somewhere else becomes a row here, in under a minute.

  1. Paste, or drop a link
    One field that accepts both and detects which it got. Paste is the reliable path; a link is a convenience that sometimes works.
  2. If it is a link, fetch it — best effort
    Many job boards block automated fetches or sit behind a login. Design for failure as the ordinary case: on any failure, fall straight through to the paste box with the link kept and a plain "Couldn't read that page — paste the description instead." Never a retry loop, never an error page.
  3. Extract the structured fields
    Title, company, location, seniority, required skills, nice-to-haves, salary if stated. Returned as a typed object, not prose, so the form fills rather than the user re-reading.
  4. Confirm before saving
    Extracted fields render as an editable form with the source text beside them. Extraction is a first draft — presenting it as fact is how a wrong company name reaches an application.
  5. Keep the original
    Store the raw description verbatim. Adverts get taken down, and at interview time it is the only record of what was actually asked for.
J12

Tailor a CV to the job

The core loop. A general CV becomes a specific one, without becoming a false one.

  1. Pick a starting point
    Reuse an existing CV, duplicate one, or start empty. Default to duplicating the closest match by role — reusing in place is offered but warned about, since it edits a document other applications may point at.
  2. Read the gap before changing anything
    The panel opens on the two-part match from §06: what the description asks for, and which of it the CV currently evidences. Requirements with no support are the whole point of the screen.
  3. Work the recommendations
    An ordered list, each one an actual edit — "Your Tokopedia role mentions queues but not Kafka, which this role names twice." Apply, Skip, or Ask me later. Every applied change is a reviewable diff.
  4. Answer the questions it can't answer
    Gaps needing facts render as inputs, not suggestions. "This role asks for team size — how many engineers did you lead?" An unanswered question stays open; it is never filled with a plausible number.
  5. Watch the score move, then stop
    The bars update as changes land. The UI should make it easy to stop at "good" — a CV optimised to 100 against one description reads like keyword stuffing to the human who eventually opens it.
J13

Draft a cover letter

From blank page to something the user is willing to sign.

  1. Collect the one thing only the user knows
    Before generating: "Why this company?" — two sentences, optional but prompted. It is the only part of a cover letter a model genuinely cannot supply, and its absence is exactly what makes generated letters interchangeable.
  2. Draft from CV + description + that note
    Streamed into a normal editor. Not a preview, not a modal — the document, editable from the first token.
  3. Flag anything unsupported
    If the letter asserts something the CV doesn't evidence, mark it inline for confirmation rather than shipping it. The letter and the CV must agree; a contradiction between them is worse than a weaker letter.
  4. Revise by instruction
    "Shorter." "Less formal." "Lead with the migration project." Applied to the current text, with undo — not regenerated from scratch, which throws away the user's own edits.
  5. Export in the format asked for
    PDF, plain text for a form field, or copy-to-clipboard. Plain text matters more than it sounds: a great many applications are a textarea.
J14

Track the outcome

Low-friction upkeep, because a tracker nobody updates is worse than no tracker.

  1. Mark it sent
    One control moves draft to applied, stamps the date, and freezes the CV snapshot. This is the moment the record becomes historical.
  2. Advance in one click from the row
    Status is an inline control in the table, not a detail-page field. Updating six applications after a busy week must not mean six page loads.
  3. Get nudged, gently
    After 21 days with no movement: a quiet row marker and one grouped prompt — "4 applications have had no reply in three weeks." Never a badge, never email by default.
  4. Close it
    Offer, rejected, withdrawn or no reply. Every negative outcome opens the reflection surface — rejected, withdrawn and no reply — and only after a beat, because nobody wants a form the second a rejection lands. This sentence used to say "only the last two", which contradicted J15, this paper's own tracker table ("only appears once the outcome is negative") and the frame, all three of which include a rejection. Corrected 18 September.
J15

Reflect on a rejection

Turn a bad day into something usable later, without making it feel like homework.

  1. Ask later, not now
    The prompt appears on the next visit, not in the moment of marking a rejection. It is dismissible and it does not come back twice.
  2. Three questions, all optional
    How far did it go? What do you think happened? What would you do differently? Structured enough to compare later, short enough to actually fill in.
  3. Keep it private and say so
    Reflections are the most personal data in the product. State plainly that they are private, never included in a CV or letter, and never sent anywhere the user didn't ask.
  4. Let patterns surface, don't diagnose
    Once several reflections exist, the companion may observe — "Four of your last six stalled after a take-home." Describe what is in the data. Never explain to someone why they are not getting hired.
06

The score, honestly

An "ATS score" is the feature most likely to be quietly dishonest. No model can know what a given employer's applicant tracking system does — vendors differ, configurations differ, and most of it is not public. A single confident number would be a fabrication with a progress bar around it.

What each half is

Machine-readability — deterministic, computed in code, no model involved

Does every section heading parse? Do employment dates parse to real ranges? Is there a contact block a parser can find? Are there multi-column layouts, tables, or text baked into images — the things that genuinely do break real parsers? This half is checkable, so it is stated as fact, and each failure names the exact element at fault.

Rules the team can write down, test, and defend. No API call.

Relevance match — estimated by the model, and labelled as an estimate

For each requirement the description states, does the CV evidence it, partly evidence it, or not mention it? Returned as a structured list — requirement, verdict, and the CV line it was matched against — so the user can disagree with any single row. The percentage is just the count of covered requirements; it is arithmetic over the list, not a vibe.

Every row cites its evidence, so the estimate is auditable rather than oracular.

Three things this feature must never do

Never claim to be a specific ATS. No "Workday score", no logos, no "your CV scored 72 in Taleo". The product does not have access to those systems and saying otherwise is a straightforward false claim.

Never show a number without what moves it. A score with no ranked, specific recommendation list is anxiety with a percentage attached. If the recommendations are empty, say "nothing worth changing" rather than displaying a bare 84.

Never reward keyword stuffing. If coverage rises while the same term is repeated, say so. Optimising a CV into something a human finds unreadable is a failure the score would otherwise call success.

07

The AI surface

Architecture notes that change the UX rather than just the code. The backend is Rust, which has no official Anthropic SDK, so these are raw HTTP calls to https://api.anthropic.com/v1/messages from backend_actix.

The key never reaches the browser

Every model call goes through backend_actix. A key in the SvelteKit client — or in a public env var — is a key anyone can extract and bill to your account. This also puts rate limiting, per-user quotas and audit logging in one place, all of which this feature needs and none of which the browser can enforce.

Four decisions that show up in the interface

Model — claude-opus-5, adaptive thinking, effort tuned per task

Drafting and tailoring want quality, so they run at high effort. Extraction from a job description is mechanical and runs lower. Effort is the lever that keeps this affordable without switching models and losing cache reuse.

"thinking": {"type": "adaptive"} · "output_config": {"effort": "high" | "low"}

Streaming for anything the user watches

Cover letters and tailoring passes stream over SSE, which is what makes the "editable from the first token" behaviour in J13 possible — and what keeps long generations from hitting request timeouts. Use a large max_tokens and stream it.

"stream": true · max_tokens ~64000 streamed · ~16000 non-streamed

Structured outputs wherever the result populates UI

Job extraction and the relevance match must come back as typed objects, not prose the frontend regexes. Constrain the response to a schema and the form fills reliably.

"output_config": {"format": {"type": "json_schema", "schema": {…}}}

Prompt caching — the CV and the description are the stable prefix

A tailoring session sends the same CV and the same job description on every turn while only the instruction changes. Put both in the cached prefix and the volatile instruction after it. This is the difference between an iterative loop being affordable and being rationed — and it is why "work the recommendations one at a time" is a viable design.

"cache_control": {"type": "ephemeral"} on the last stable block · verify usage.cache_read_input_tokens

Job description by URL

Claude's server-side web fetch tool handles the link case — it fetches URLs already present in the conversation, so the pasted link is the input. Constrain it with an allow-list and treat every failure as the ordinary path back to paste. 

// backend_actix → api.anthropic.com/v1/messages
{
  "model": "claude-opus-5",
  "max_tokens": 16000,
  "tools": [{ "type": "web_fetch_20260209", "name": "web_fetch",
              "max_uses": 1 }],
  "output_config": {
    "format": { "type": "json_schema", "schema": {
      "type": "object",
      "properties": {
        "title": {"type": "string"}, "company": {"type": "string"},
        "location": {"type": "string"}, "seniority": {"type": "string"},
        "required_skills": {"type": "array", "items": {"type": "string"}},
        "nice_to_have":   {"type": "array", "items": {"type": "string"}}
      },
      "required": ["title","company","required_skills","nice_to_have"],
      "additionalProperties": false
    }}
  },
  "messages": [{"role":"user","content":"Extract this posting: https://…"}]
}

Two things to know: a server-tool failure arrives as HTTP 200 with an error object inside the result block rather than a raised error, so the handler must branch on the block's content — and many job boards will simply refuse. Both are why J11 treats paste as the primary path and the link as a shortcut that sometimes pays off.

08

What the backend needs

None of this exists yet. R15 onward, continuing the API Requests numbering — and now formally filed in Blogport API Round Two, which is the live version of this list. Round one's fourteen requests all shipped in the meantime.

Two things round one changed for this paper

The media work landed. PATCH /api/media/{id}, restore and hard delete all exist, so anywhere this paper treats media as write-once it is now out of date — alt text is correctable, and media follows the same archive ladder as everything else.

Public media shipped as a redirecting path, which means an uploaded CV photo or a job-related image renders on a public page without a signed URL in the markup. That was the one thing standing between this design and being demonstrable.

R15 · Jobs and applications

The core tables. A job holds the raw description plus extracted fields; an application joins a job to a CV snapshot with status, dates and next action. Standard CRUD following the existing module conventions.

/api/jobs · /api/applications — list, get, create, patch, archive, restore

R16 · CV snapshots

The freeze in J14. An immutable copy of a CV at the moment of applying, addressable forever and never edited. Not a new CV row — a versioned artifact the application points at.

POST /api/cvs/{id}/snapshot → { snapshot_id } · GET /api/cv-snapshots/{id}

R17 · Cover letters

Scoped to an application, with a content language. Same tri-state PATCH semantics as blog posts so partial saves behave predictably.

/api/applications/{id}/cover-letter

R18 · The AI proxy

The one that gates everything else. Server-side calls with the key held in backend_actix, SSE passthrough for streaming, per-user quotas, and a stored record of each generation for cost attribution. Needs its own error codes for refusal, upstream rate limits and timeouts — the blueprint's rule that no raw code reaches the screen applies here too.

POST /api/ai/extract-job · /ai/suggest · /ai/tailor · /ai/cover-letter (SSE) · /ai/reflect

R19 · Match analysis

Both halves of §06 behind one call: the deterministic readability rules run in Rust, the relevance match goes out to the model, and the response keeps them separate all the way to the UI. Cache the result against the CV and job version so re-opening a row is free.

POST /api/applications/{id}/analysis → { readability: {...}, relevance: {...}, recommendations: [...] }

R20 · Locale and content language

user.locale for the interface — which finally gives PUT /api/users/me a second editable field — plus a language column on CVs and cover letters for content. Two nullable columns and a field on an existing endpoint.

user.locale · cv.language · cover_letter.language

R21 · Reflections

Attached to an application, private by construction, and never included in any prompt that produces user-facing content unless the user explicitly asks for the pattern summary in J15. Worth an ADR — it is the most sensitive data the product will hold.

/api/applications/{id}/reflection

Sequencing

R18 first — nothing else in this paper can be demonstrated without the proxy, and its quota and error handling shape every AI surface. Then R15 + R16 together, since a tracker row is meaningless without the snapshot. Then R19, which is where the design risk in §06 actually gets tested. R17 and R21 follow easily once the shapes exist. R20 is independent and can land any time — and the frontend can build both language surfaces against a local preference before it does.

Two questions to settle before R18 is written

Who pays, and what happens at the limit? Generation has a real per-call cost. Whether this is a fixed monthly allowance, a credit balance, or unmetered changes the interface substantially — a quota needs a visible remaining count and a graceful refusal state, and neither can be retrofitted onto screens that assume calls are free.

Is the user's CV retained by anything outside your database? The answer is no by default, and the product should say so plainly on the AI surfaces. People paste their entire employment history into this; being explicit about where it goes is not legal boilerplate, it is the reason they will use it.
