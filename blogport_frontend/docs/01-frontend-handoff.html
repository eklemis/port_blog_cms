02

The auth and session contract

Read from jwt_config.rs, refresh_token.rs and logout_user.rs rather than inferred. These are the numbers the session layer has to be built against.

Token Default lifetime Env override Notes
Access 1800s — 30 min JWT_ACCESS_EXPIRY Hard-capped at 24h by a startup assertion
Refresh 604800s — 7 days JWT_REFRESH_EXPIRY Must exceed the access expiry or the server panics on boot
Email verification 86400s — 24 hours JWT_VERIFICATION_EXPIRY Drives the "link expired" branch in J1
Password reset 3600s — 1 hour JWT_PASSWORD_RESET_EXPIRY Drives the J3 expiry copy

The old cookie durations were wrong in both directions

cookies.server.ts set the access cookie to 15 minutes against a 30-minute token — throwing away half of every session — and the refresh cookie to 14 days against a 7-day token, so for a full week the browser held a cookie the server had already stopped honouring. That second one produces the worst failure mode available: a user who looks signed in and is not.

Derive both maxAge values from the same source as the backend, or read exp off the token. Do not hardcode a third opinion.

Three behaviours to build against

Question Answer What the frontend must do
Does refresh rotate? Yes, by default Every POST /api/auth/refresh returns a new refresh token, and the old one is not blacklisted. Persist both tokens on every refresh — dropping the new refresh token silently pins the session to the original 7-day window.
What does logout kill? One refresh token Single session, not all devices. Don't offer a "sign out everywhere" control — nothing backs it.
Can logout fail? No A missing or unverifiable token is logged and still returns 200. J2's "clear local state regardless of the response" is safe, and now confirmed rather than defensive.

Access tokens are never blacklisted

Logout blacklists the refresh token only. An access token stays cryptographically valid for up to 30 minutes after sign-out, so what actually ends the session in the browser is clearing the cookie. That is an argument for the server-route proxy, not against it — with httpOnly cookies the token is gone from the client the moment it is cleared.

03

Validation rules

Mirror these client-side so the blueprint's field-level errors resolve without a round trip. Read from the use cases and services, not from the OpenAPI examples — which are misleading in one important case.

Field Rule Normalisation Error code
username 3–50 chars, [A-Za-z0-9_] only trimmed, lowercased INVALID_USERNAME
email RFC-valid address trimmed, lowercased INVALID_EMAIL
password 12–128 chars. Length only. none INVALID_PASSWORD
full_name non-empty, max 100 chars trimmed INVALID_FULL_NAME
slug 1–200 chars, [a-z0-9-] only trimmed, lowercased server-side INVALID_SLUG
title non-empty, max 200 chars — EMPTY_TITLE · TITLE_TOO_LONG
upload ≤ 5 MB · ≤ 6000 px per side · JPEG, PNG, WebP extension must match MIME FILE_TOO_LARGE · INVALID_DIMENSIONS · INVALID_MIME_TYPE · MIME_EXTENSION_MISMATCH

The password rule is length only — don't invent complexity

BasicPasswordPolicy checks nothing but 12 ≤ length ≤ 128. No uppercase, digit or symbol requirement exists. The OpenAPI example value is SecurePass123!, which strongly implies complexity rules and will mislead anyone who designs the field from the spec alone.

Show "At least 12 characters" and nothing more. A client-side complexity rule the server does not enforce rejects passwords the backend would happily accept — the frontend inventing its own policy is a real bug, not a safety net.

Slug normalisation is server-side, but do it client-side anyway

The server trims and lowercases before validating, so My-Post is accepted and stored as my-post. Normalise in the field as the user types instead: the slug becomes the public URL, and a field that silently changes its value after save is the kind of small dishonesty that erodes trust in an editor.

04

Do not build these — four remain

Each is a control a competent developer will reach for because the surrounding patterns imply it, and none has an endpoint. This list was eight; backend round one shipped four of them. What survives is below; what was released is in the note under it.

Change email or password while signed in

no endpoint

PUT /api/users/me accepts full_name and nothing else. Password changes go out through the forgot-password flow. Render email and username as read-only facts, not disabled inputs.

Sign out of all devices

single session

Logout blacklists the one refresh token it was handed. There is no all-sessions revocation to hang a control on.

An "all media" library view

no endpoint

Listing is by-target only. A combined library means four parallel calls merged client-side with no paging — scope it as a per-target picker instead.

Reactivating a closed account

no endpoint

DELETE /api/users/me is one-way from the UI's side. The confirmation copy must say reopening requires contacting support.

Now released — build these, they were on the list above

Backend round one shipped every request we filed, and four of them retire an entry from this page. Resend verification — POST /api/auth/email-verification/resend, so the hold screen's button is real. Project restore — POST /api/projects/{id}/restore, so projects follow the same archive ladder as everything else. Topic rename — PATCH /api/topics/{id}, retiring the create-retag-retire workaround. Media metadata and lifecycle — PATCH /api/media/{id} plus restore and hard delete.

Two earlier corrections still stand: public topic chips and paging already worked — both public listings accept search, topic_id, sort, page and per_page; and media deletion was always soft, so nothing was ever destroyed by a delete.

Fixed: blog search is no longer case-sensitive

Blog search used a case-sensitive match while project search did not, so Rust missed “rust and the borrow checker”. Both behave the same way now, and the API did not change — the same request simply returns more. Do not add client-side case normalisation; there is nothing left to paper over.

One rule reversed: alt text is no longer permanent

The Forms Spec required alt text at upload and called it the only chance, because no PATCH on media existed. It does now. Keep the field required at upload — that is the moment someone is actually looking at the image — but drop any copy calling it permanent, and give the media library an edit affordance.

Whether position is patchable alongside alt_text is still unconfirmed. Until it is, treat upload order as display order and do not build drag-to-reorder.

05

Setup

Four things to do before the first component.

1 · Drop in the theme

theme.css ships alongside this document. It is the merged token set — existing arch palette, the five status values, the mono family — plus the component grammar extracted from the old login form. Import it once; never hardcode a hex value in a component. Use v3 or later: earlier copies carry pre-audit colour values that fail WCAG AA.

2 · Wire type generation

v1.ts is generated and marked "do not edit", but the old repo had no script to regenerate it. Add one now, or it goes stale the first time the backend adds a route: 

// package.json
"scripts": {
  "gen:api": "openapi-typescript http://localhost:8080/api-docs/openapi.json -o src/shared/api/v1.ts"
}

3 · Point at an API

VITE_BACKEND_BASE_URL is the only variable the frontend needs; it defaults to http://localhost:8080. Running the backend locally additionally requires Postgres, Redis, SMTP and GCS credentials, plus cargo run -p migration -- up — migrations are never automatic. For frontend-only work a seeded staging URL is the better answer.

4 · Confirm the email link targets

VERIFICATION_HANDLER_URL and PASSWORD_RESET_HANDLER_URL are backend env vars holding frontend routes — they are what the emailed links point at. If they don't match the SvelteKit routes you build, J1 and J3 break in a way that looks like a frontend bug and isn't. Agree the paths before building those screens.

Still needed from you

This section held three open questions. Two were answered by backend round one and the third — the one that blocked the largest dependency in the app — is now decided. What is left is the checklist for day one.

The content format — decided: Markdown

GitHub-Flavoured Markdown, stored as source and never as rendered HTML, raw HTML disabled, rendered server-side in +page.server.ts. The editor is source-first with a live preview, not a WYSIWYG. excerpt stays plain text — it feeds the meta description. One consequence needs reading before you build the editor: media read URLs are signed and expiring, so an image URL cannot be written into the markdown source. Full detail in the Forms & Interaction Spec.
