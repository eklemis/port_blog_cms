Fifth paper · the missing half

Forms and Interaction Spec

The Console Blueprint says which components exist and the Frontend Handoff says what the API will accept. Neither says what a form contains, what a component does when you touch it, or when an error is allowed to appear. That is this document.

Updated after backend round one. Media metadata became patchable, so alt text is no longer permanent and the ordering rule is now conditional — both are marked at the point of change rather than quietly rewritten.

01

Field types, defined once

Twenty-two forms share nine input types. Specify behaviour here and every form below is a field list rather than a fresh design problem.

Type Behaviour Validates Used by
text Single line. Trims on blur. Character counter appears at 80% of any max length. on blur title, full_name, company
slug Normalises as you type — lowercase, spaces to hyphens, strips anything outside [a-z0-9-]. Auto-derives from title while the record is a draft; the link breaks on first manual edit and never re-derives. on blur + availability check debounced 400ms post, project
email inputmode="email", no autocapitalise. Never validated per keystroke — half a typed address is not an error. on blur register, login, reset
password Single field with a reveal toggle. Never a confirm-password twin. Requirement text visible from focus, not after rejection. on blur register, reset

markdown Source-first editor with a live preview pane — not a WYSIWYG. GitHub-Flavoured Markdown: fenced code blocks, tables, strikethrough, task lists. Two of these carry a rule the API cannot enforce

Alt text is required by this spec, not by the backend. POST /api/media/upload-url accepts a null alt_text. Backend round one added PATCH /api/media/{id}, so it is correctable now — but the picker is the moment someone is actually looking at the image, and a field they will never revisit is how images ship without alt text at all.

Password is one field, not two. The confirm-password twin exists to catch typos in a masked field — a reveal toggle solves the same problem without doubling the typing and without a second error state that means nothing to the person reading it.

03

The three forms worth specifying in full

Register, the post editor and media upload. The rest follow from the field-type table; these three each carry a rule that would otherwise be guessed.

Register

Field Type Required Rule Error copy
username text yes 3–50, [A-Za-z0-9_], lowercased server-side “Letters, numbers and underscores only.”
email email yes RFC-valid “That doesn’t look like an email address.”
full_name text yes non-empty, ≤ 100 “Please add your name.”
password password yes 12–128 characters. Length only. “At least 12 characters.”

Username is permanent — it becomes the public URL. Say so under the field before submission, not in a confirmation dialog after. Do not add uppercase/digit/symbol rules: the server does not enforce them, and a client-side rule the API disagrees with rejects passwords the backend would have accepted.

Post editor

Field Type Required Rule Behaviour
title text yes non-empty, ≤ 200 Counter from 160. Autosaves.
slug slug yes ≤ 200, [a-z0-9-], unique per author Auto-derives while draft. Once published, moves behind a “Change address” disclosure that states the consequence.
excerpt textarea no plain text null clears it — tri-state PATCH
content markdown yes GFM. Raw HTML disabled. 2s idle autosave; stored as the markdown source, never as rendered HTML
topics combobox no own topics only Each chip is its own request; one failure doesn’t roll back the others
published_at datetime no null = draft, future = scheduled Set by Publish / Schedule, never typed directly

Markdown breaks one thing: you cannot put an image URL in the source

Media read URLs are signed and expiring — GET /api/media/{id}/{size} returns a URL with an expires_at. Writing that URL into ![alt](https://storage.googleapis.com/…) bakes a dead link into the stored document. The post would render correctly for an hour and be broken forever after.

Store a stable reference and resolve it at render time. The editor's Insert image action opens the media picker and writes ![alt](media:8f1b2c3d); the renderer rewrites the media: scheme into a real URL on the way out — a signed one in the console preview, a public one on the public page. This is also the only shape that survives the public-media work in R1, since the two surfaces need different URLs for the same image.

Consequence for the editor: Insert image is a real control, not something people type by hand. Typing a raw external URL still works and is left alone — only the media: scheme is rewritten.

What else the Markdown decision settles

Render on the server. Markdown → HTML happens in SvelteKit's +page.server.ts, not in the browser. Public pages stay server-rendered with real metadata (J9), and no parser ships to the reader.

Raw HTML off, and sanitize anyway. GFM permits inline HTML; disable it. The author is the only writer today, so this is defence in depth rather than an XSS fix — but it becomes load-bearing the moment anything else can write a post.

Code blocks need highlighting, and this audience will notice. Highlight at render time on the server rather than shipping a client-side highlighter. excerpt stays plain text — it goes into the meta description, where markdown syntax would leak as literal characters.

The cover letter uses the same editor for consistency, but exports differ: PDF renders the markdown, and “Copy as text” must strip the syntax — a great many application forms are a plain <textarea>, and pasting **bold** into one looks careless.

Inserting an image into a post

Three entry points, one flow. All of them converge on the same dialog, because the alt text moment is the one that cannot be repeated.

Step What happens Why it is this way
1 · Trigger Toolbar Insert image, paste from the clipboard, or drag-drop a file onto the editor. Paste is the one that matters most — a developer blogging about their own work screenshots constantly. Making it work is worth more than the toolbar button.
2 · Validate locally ≤ 5 MB, ≤ 6000 px per side, JPEG/PNG/WebP — checked in the browser before any request. All three limits are knowable client-side. Rejecting a 12 MB file instantly beats a round trip that fails.
3 · Ask for alt text A small dialog: thumbnail preview, alt text (required), caption (optional). Confirm is disabled until alt text is non-empty. The best chance, no longer the only one. PATCH /api/media/{id} can correct it later, but nobody goes back. Showing the image beside the field is what makes writing it easy rather than a tax.
4 · Request the upload URL POST /api/media/upload-url with attachment_target: BlogPost, the post id, and role: Inline. Inline is a distinct role from Cover — the same post has both, and they render differently.
5 · Insert the reference immediately At the cursor, on its own line with blank lines around it:
![Hexagonal layout of the API](media:8f1b2c3d) 		The media_id comes back with the upload URL, before the bytes finish uploading. So the document is correct instantly and the writer keeps typing.
6 · Upload in the background PUT to the signed URL. The preview pane shows a pending tile where the image will land; the source pane shows the markdown line. This is the only progress that can be measured honestly, so the determinate bar lives on the tile — not on the editor.
7 · Resolve on ready Poll GET /api/media/{id}; on ready the preview swaps the tile for the real image. The source never changes. Only the preview resolves — which is exactly the split the media: scheme buys.
8 · On failure The markdown line stays. The preview tile turns failed with Retry and Remove. Never silently delete a line the writer put in their document. A visible broken image is recoverable; a vanished paragraph is not.

Five decisions inside that flow

The alt text is the readable half of the line. media:8f1b2c3d is an address, not a word — so the alt text is what makes ![Hexagonal layout of the API](media:8f1b2c3d) mean something when you reread your own source six months later. Another reason to require it.

Deleting the line does not delete the asset. Removing text is instant, local and undoable; deleting an upload is none of those. Orphaned media is a job for the media library, not a side effect of pressing Backspace.

Typed external URLs are left alone. Only the media: scheme is rewritten. ![chart](https://example.com/x.png) passes through untouched.

Reuse is a second tab in the same dialog — “Upload new” and “Already uploaded”, the latter from GET /api/media/by-target/blog_post. Note that route takes the target type, not an id, so the list is every image across all your posts. That is fine for reuse and impossible to scope tighter until the API offers it.

Ordering is upload order, for now. Whether position is patchable alongside alt_text is unconfirmed (filed as C2). In a post it barely matters either way — the markdown line position decides where the image appears. It matters for project galleries, which is where drag-to-reorder would land if the answer is yes.

Until R1 ships, inline images do not appear on the public page

The public blog response carries no media and the variant route needs a verified session. So an image inserted today renders in the editor preview and is invisible to readers.

The editor must say so at the point of insertion — a one-line note in the dialog, not a banner somewhere else. Writers will otherwise publish posts with holes in them and have no way to find out. Remove the note when R1 lands.

05

When errors are allowed to appear

The most common form-design mistake in this product would be validating too early. A rule that fires while someone is still typing calls them wrong for being halfway through a word.

Never on keystroke

No field validates per character. j is not an invalid email; it is the first letter of one. The only per-keystroke feedback allowed is positive — a slug normalising, a counter counting.

On blur, once touched

A field validates when it loses focus and only if the person has typed in it. An untouched empty required field is not an error until submit.

On submit, everything

Submit validates all fields, focuses the first invalid one, and scrolls it into view. If the server rejects, the form keeps every value — losing a filled form to one bad field is the worst outcome available.

Debounced for anything remote

Slug availability at 400ms idle. Search at 300ms. Never on every keystroke — that is a request per character and a rate limit waiting to happen.

Clear on the next success

An error clears when the field next blurs valid — not on focus, which would hide the message the moment someone returns to read it.

One message per field

Server and client errors occupy the same slot. If both exist, the server's wins — it is the one that actually blocked the write.

Keyboard and focus

The Console Blueprint asserts that keyboard support is not a phase two, then doesn't say what the keys do. Here they are.

Context Key Does
Any form Enter Submits from a single-line input. Never from a textarea or richtext.
Esc Blurs the field; a second press closes the surrounding dialog if there is one
Dialog Tab Cycles within the dialog only — focus is trapped
Esc Cancels and restores focus to the control that opened it
Enter Nothing on a destructive dialog. Confirm is reached by Tab, deliberately.
Combobox ↓ ↑ Moves through options; opens the list if closed
Enter Selects the highlighted option, or creates when on “Create «…»”
Backspace On an empty input, removes the last chip
Esc Closes the list, keeps the selection
Editor ⌘S Forces a save. Intercepted — never the browser's save dialog.
⌘Z Undoes the last applied AI suggestion as one unit, not character by character
Table Tab Moves between the row's interactive controls, not every cell
Enter Opens the focused row's detail

Focus order follows reading order, always

In the CV builder, that means a repeatable row's fields come before its Remove button, and Remove comes before the next row's fields. Any place where a floating action or a sidebar breaks that order is a bug, not a layout choice.

Every focusable element shows the 2px accent-ink ring. It is defined once in theme.css under :focus-visible — do not override it per component, and never set outline: none without an equivalent replacement.

07

What happens after “Export PDF”

A button that fires a silent browser download is the most common way a good editor ends badly: the file lands somewhere the person didn't choose, styled in a way they never saw. Export is a three-state sequence, not a click.

State Shows Why
1 · Options A modal: paginated preview on the left, options on the right — paper size (A4 / US Letter), file name, page count. Primary action Download. The preview is the point. Pagination is the thing people cannot predict, and a cover letter that silently runs onto a second page is a bad outcome they'd want to catch first.
2 · Building Download disabled with a spinner and “Building your PDF…”. Suppressed entirely under 400ms so fast exports don't flash. Rendering is real work. An unresponsive button with no explanation reads as broken.
3 · Saved The modal stays open: “Saved to your downloads”, the file name, and Open / Done. Browser downloads are easy to miss. Naming the file is how someone finds it. The modal never closes itself — auto-dismiss removes the only confirmation that anything happened.

Three rules for this modal

Say where the file is built. “Nothing leaves your account — the file is built in your browser.” People exporting a CV or a cover letter are handling their employment history; one sentence is worth more than a privacy page.

Copy as text is a sibling, not a lesser option. Most application forms are a plain <textarea>. That path strips the Markdown syntax and confirms with a toast — it needs no modal at all.

Failure keeps the document. If rendering fails, the modal shows the error and a Retry. It never closes and discards the state the person configured.

Where the companion appears

The rail is the same component everywhere — deliberately

A person who learns Apply / Skip while tightening a blog sentence already knows how to work a CV tailoring pass. If the post editor got a chat box and the CV editor got a diff panel, that transfer is lost and each surface has to be learned separately.

So the rule holds across all three documents: the companion proposes into a reviewable change, never overwrites; a gap that needs a fact renders as an input, not a sentence; and every applied change is one undo away for the whole session.

09

Responsive

Both widths are drawn: 35 screens at 1180px and the same 35 at 390px. One width is not drawn — all three widths now are. The six transformations below are still what an implementation follows, and what a new screen should be designed against.

Width Status Behaviour
< 768px drawn 35 screens at 390 × 844, light and dark. Tab bar, cards, bottom sheet.
768 – 1023px drawn Tablet. 35 screens at 834 × 1112, light and dark. Sidebar collapses to a 64px icon rail; tables keep the three load-bearing columns and drop the middle; the right rail stays a rail rather than becoming a sheet. These were a rule with no frames behind them until the deliverables audit; they are now drawn.
≥ 1024px drawn 35 screens at 1180 wide, light and dark.

No width may be answered with a wall

Nothing in this product may respond to a viewport with “please use a larger screen”. That applied when fifteen screens were undrawn and it still applies at tablet, and to any screen added after this document.

Where no frame exists, apply the transformations below. The result will be tighter than a drawn design, and it will work — that is the bar.

The six transformations

Every mobile frame in the file is these six rules applied. A screen designed later should be reflowed the same way rather than invented from scratch.

Tables become cards

Five columns cannot survive 390px. Each row becomes a card: the identifying field and the status on one line, the secondary identifier beneath, the action and date in a footer. Columns that were only useful in aggregate are dropped, not shrunk.

The right rail becomes a tabbed bottom sheet

Tabbed, not stacked. Three cards below the editor would bury the thing being edited; a sheet keeps the document in view and the tabs keep the rail's sections reachable.

The sidebar becomes a five-item tab bar

Everything else goes behind More. Account and settings live there rather than competing for a slot with what people open daily.

Body type goes up, not down

15.5px on a post, 14px on cards. Shrinking text to fit a small screen is the reflex and it is wrong — at a 350px measure, larger type is what holds the line near sixty characters.

Primary actions go full width

Secondary actions pair up beside each other. Thumb reach beats visual balance on the one control someone opened the screen to press.

Filter chips scroll, never wrap

A wrapped filter row pushes the first result below the fold, which defeats the purpose of an index. Horizontal scroll keeps the content visible.

Five things drawing the hard screens changed

An earlier version of this section argued fifteen screens should stay undrawn because a phone version would be “an invention rather than an adaptation”. Drawing them disproved that in four places and confirmed it in one.

Screen What changed
Tailor CV The hierarchy inverts. On desktop the CV is primary and the match panel is the rail. At 390px that is backwards — you open the screen to see the match — so the two bars go to the top, suggestions become cards, and the CV moves behind a tab. The desktop layout implied a priority the phone does not share.
AI assist The floating toolbar has nowhere to go. There is no room to hover a bar above a text selection at this width, so it becomes the sheet header instead. The selection highlight stays; the toolbar migrates.
Export PDF The preview survives the reflow. It was the obvious thing to drop for space. It is also the entire reason the modal exists — pagination is what nobody can predict — so the sheet keeps it and sheds the options instead.
Topics Usage counts move onto the name line. There is no fourth column at 390px, and the count could not simply be dropped: it is what makes Retire safe to press.
CV builder The one where the original worry held. Five sections reflow to an accordion, one open at a time, and it works. It is also plainly a compromise — a stepped wizard would serve this form better. The accordion is drawn so the fallback is concrete, but treat it as a placeholder for a product decision, not as the answer.

Why the frames exist rather than just the rules

Six rules and a paragraph of reasoning is a specification a developer has to interpret. A drawn frame is one they can implement. The four findings above were all invisible until the screens were drawn — which is the argument for drawing them, and against trusting a rationale that explains why something need not be.

State of the Figma file

One Theme collection, two modes, 17 variables including the modal scrim. Every fill and stroke in the file resolves through it, and every variable carries WEB code syntax — so Dev Mode emits var(--color-arch-bg) rather than a hex. The unbound-colour count is zero, and it is worth re-running after any bulk change: adding the icons silently introduced 386 unbound paints, and nothing else would have caught it. The count excludes IMAGE paints, which are photographs and bind to nothing.

216 frames, none detached, no overlaps. Auto layout throughout, so padding and gap are real and there are no redline annotations to maintain. The tablet set was produced by transforming the desktop frames rather than redrawing them, so every instance and variable binding survived intact.

Placeholder imagery is real photography — 88 fills across 44 positions, seeded by each node’s structural address so a light frame and its dark twin always carry the same picture. Media tiles are filled only in ready; uploading, processing, failed and archived stay grey, because a thumbnail is exactly what those states do not have yet. The photographs are Unsplash-licensed placeholders for the mockup, not shipping assets.

The prototype is wired. 376 links on 376 distinct nodes, grouped into six named flows, in both themes — sidebar, public header, the auth chain and the Career Studio hub. Four connections are deliberately absent; the Prototype Map says which and why.

Six colour tokens changed. The palette was audited pair by pair against WCAG 2.2 AA and 21 of 62 pairs failed. All six failing values were corrected in the Theme collection and a new arch/line-control token now carries control boundaries at 3:1. Any theme.css pulled before that audit is stale.

Two deliberate deviations. The component sets share one Component Library page rather than one page each — splitting them would separate each set from its dark preview. And the dark frames are clones with a mode override rather than instances, so an edit to a light frame does not propagate; that keeps them independently editable, which is what a mockup wants.

One thing Figma cannot show, and it is not a design gap

A swapped icon inside a Button reverts to the muted stroke rather than inheriting the button’s text colour — an instance-swap brings its own styling. Each variant’s placeholder is tinted per kind so the default state is right.

In the implementation this disappears entirely: Lucide renders with currentColor, so an icon inside a button inherits the button’s colour for free. That is why there is no per-kind icon variant, and why building sixteen would be solving a problem that does not exist in code.
