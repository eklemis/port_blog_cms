Blogport Console Blueprint

Every capability backend_actix exposes today, arranged into the paths a person actually walks — and the rules that keep those paths feeling like one product. Fifty-two routes across seven domains, drawn in the charcoal-and-amber system already sitting in layout.css.

Two facts shape everything

Every authoring route is guarded by the VerifiedUser extractor, and media processing is asynchronous. Ignore either and the UI lies to people.

Nothing invented

Each journey step names the endpoint that backs it. Where a step has no endpoint, it is listed in Gaps instead of quietly designed around.

Two audiences, one API

The authenticated console under /api/* and the anonymous reader under /api/public/*. They share a design language, not a shell.

The accent is a verb, never a status

02

The gate that decides the whole product

POST /api/auth/login succeeds for an unverified account and hands back a working access token. Every route that creates, edits or uploads anything then refuses it with 403 EMAIL_NOT_VERIFIED. A console that treats "logged in" as "can work" will show a person a full authoring UI that fails on every button.

What the design owes the unverified state

A dedicated hold screen at /verify, not a dashboard with dead buttons. It shows the address the link went to, a "Resend" affordance, and an escape. The screen carries no nav at all — wordmark and locale switcher only. An earlier draft of this document said the nav renders read-only with profile reachable; the frames never did that, and the frames are right. A hold screen is a hold screen, not the console with most of it disabled.

The escape is "Sign out", not "Use a different address". Changing your address while signed in has no endpoint, so an address-change control here would promise something the API cannot do. Signing out and registering again is the journey that actually exists, and it is the one the frame now offers.

Verification is a plain GET with the token in the path, so the emailed link can land directly on a frontend route that calls it and renders three outcomes: verified, already verified (treat as success — do not scold), and expired or invalid (offer resend).

Public routes are keyed on username, and username is immutable

PUT /api/users/me accepts full_name and nothing else. Every public URL an author shares therefore stays valid forever, which is a genuine promise worth making out loud on the account screen: "Your public address is /janedoe. It never changes." Do not render username as an editable field that silently discards the edit.

04

The ten journeys

Numbered because they are genuinely ordered — each step's outcome is the next step's input. Failure branches carry the error code that produces them and the exact recovery the UI offers; an error with no listed recovery is a bug in this plan.

J1

Get an account

Stranger → verified author who can publish. The only journey that crosses both gates.

  1. Register
    Four fields: username, email, full name, password. Validate username and password inline before submit — the server has distinct codes for each and the person should never learn them one round-trip at a time.
    POST /api/auth/register → 201 { message, user }
  2. Land on the hold screen, not the dashboard
    Registration returns a user, not a token. Route straight to /verify showing the address the mail went to. This is the screen that does the waiting, so it must be worth looking at: what verification unlocks, and a resend.
  3. Open the emailed link
    Lands on /email/verification/[token], which calls the API and renders one of three outcomes. "Already verified" is a success, not an error.
    GET /api/auth/email-verification/{token}
  4. Sign in
    Store the access token in memory and the refresh token in an httpOnly cookie via the SvelteKit /api route — the pattern shared/auth/cookies.server.ts already establishes.
    POST /api/auth/login → { access_token, refresh_token, user }
  5. First run: three things, then get out of the way
    A dismissible checklist on /studio — create a topic, write a first post, add a résumé. It disappears for good once any two are done; it is not a permanent fixture.
Branches
USER_ALREADY_EXISTS
409 on register. Keep the form filled, mark the email field, and offer "Sign in instead" and "Reset your password" as buttons — the person almost certainly has an account they forgot.
INVALID_PASSWORD
400. The server's message names the failed rule. Show it under the field and keep the requirements visible from the moment the field is focused, not only after a rejection.
RATE_LIMITED
429 after 5 registrations per hour. Read Retry-After and render a real countdown: "Too many sign-up attempts. Try again in 42 minutes."
INVALID_TOKEN · TOKEN_EXPIRED
Verification link is stale. The dead-end to avoid. Show "This link has expired" with a resend button on the same screen — never bounce back to login.
J2

Stay signed in, then leave cleanly

The journey nobody should ever notice. Success is measured in absent interruptions.

  1. Refresh silently, ahead of expiry
    Schedule the refresh from the access token's own exp, at roughly 80% of its life. Do not wait for a 401 to discover the token died mid-keystroke.
    POST /api/auth/refresh — 30 per 5 minutes
  2. Queue in-flight requests during a refresh
    One refresh at a time; other calls wait and retry once. Ten parallel refreshes on a dashboard load will burn the rate limit and log the person out for being busy.
  3. On an unrecoverable 401, save the destination
    Redirect to login with the intended path preserved, and say why: "Your session expired. Sign in to pick up where you left off." After login, return them there.
  4. Log out
    The refresh token is blacklisted in Redis server-side. Clear the cookie and in-memory token regardless of the response — a failed logout call must never trap someone in a session they asked to end.
    POST /api/auth/logout
Branches
USER_DELETED
403 on any call. The account was soft-deleted. Clear everything and route to /account/closed — do not loop through login. Copy: "That account has been closed. If this is a mistake, contact support."
INVALID_TOKEN_TYPE
An access token was sent where a refresh token belongs. A client bug, not a user error. Log it, force a clean re-login, and never show the code.
Network failure on refresh
Not a logout. Retry with backoff and show an unobtrusive "Reconnecting…" strip. Discarding a person's unsaved editor because Wi-Fi blinked is the worst thing this app can do.
J3

Recover a password

Locked out → signed in, without the flow confirming to a stranger whether an address is registered.

  1. Ask for a reset from the login screen
    "Forgot password?" sits beside the password field, not buried in a footer.
    POST /api/auth/password-reset { email } — 5 per hour
  2. Show the same confirmation either way
    "If an account exists for that address, a reset link is on its way." Never branch the copy on whether the address was found — that turns the form into an account-enumeration oracle.
  3. Set a new password
    Token comes in from the path. One password field with a reveal toggle, not two fields to mistype in parallel.
    POST /api/auth/password-reset/{token} — 10 per hour
  4. Route to login, prefilled
    The reset does not return tokens. Confirm success, prefill the email, and put focus on the password field.
Branches
INVALID_RESET_TOKEN
401. "This reset link is no longer valid — they expire after a short window." Offer to send a fresh one from that same screen.
INVALID_PASSWORD
400. Keep the token in the URL and let them retype. Losing a valid token to one weak password is a needless restart.
J4

Publish a post

The flagship loop. Blank page → live at /{username}/{slug}, and back again if needed.

  1. Create the draft first
    Title, slug, content. Omitting published_at creates a draft. Creating early matters: media attaches to a target_id, so a post must exist before it can have a cover image.
    POST /api/blog → 201 { id }
  2. Derive the slug, let it be overridden, then lock it
    Auto-slug from the title while the post is a draft. Once published, editing the slug breaks a live URL — move it behind an "Change address" disclosure with that consequence stated.
  3. Write, saving as you go
    PATCH on a two-second idle debounce. The status line reads Saving… → Saved 10:42 → Unsaved changes, and it is the only place that reports save state.
    PATCH /api/blog/{id}
  4. Attach topics
    A combobox over GET /api/topics that can create a topic inline. Attaching is its own call, so each chip resolves independently and a duplicate failure does not roll back the others.
    POST /api/blog/{id}/topics · DELETE /api/blog/{id}/topics
  5. Add a cover image
    Runs J8 with attachment_target: BlogPost, target_id = this post, role: Cover. The tile shows a processing state; publishing is not blocked on it.
  6. Publish, or schedule
    One control with two outcomes: "Publish now" sets published_at to now; "Schedule" sets a future timestamp. A future date means the post goes live with no further call — the UI must say so plainly, because nothing will happen on screen when it does.
    PATCH /api/blog/{id} { published_at }
  7. Confirm with the real address
    The success toast carries the public link, and the editor header switches to a live pill with "View" and "Unpublish".
Branches
SLUG_ALREADY_EXISTS
409. Slugs are unique per author. Mark the field, suggest an available variant (-2), and never lose the draft body to a slug collision.
TITLE_TOO_LONG · EMPTY_TITLE
400, 200-char cap. Show a live counter from 160 characters onward rather than rejecting at submit.
POST_UNAUTHORIZED
403 — someone else's post. Only reachable via a pasted URL. Show a plain "You don't have access to this post" page with a route back to the list.
Autosave fails
Keep the buffer. Switch the status line to "Couldn't save — retrying" in the danger colour, retry with backoff, and block navigation with a confirm while changes are unsaved.
J5

Ship a project entry

A piece of work → a public project page with stack, links and screenshots.

  1. Create with the essentials
    Title, slug, description, tech stack, and optional repository and demo URLs. tech_stack is a string array — a chip input, not a comma-separated text field people have to guess the delimiter for.
    POST /api/projects → 201 { id }
  2. Add screenshots
    J8 with attachment_target: Project and role: Screenshoot. PATCH /api/media/{id} now exists, so metadata is editable. Whether position is in that patch set is unconfirmed — until it is, treat upload order as display order and hold the drag-to-reorder.
  3. Tag it
    Same topic component as posts, same vocabulary. A topic used on a project appears in the post filter too — one taxonomy, two surfaces.
    POST · GET · DELETE /api/projects/{id}/topics
  4. Refine
    PATCH only. Unlike CVs there is no full-replace PUT, so the editor is field-level throughout and never sends an object it did not load first.
    PATCH /api/projects/{id}
Branches
No draft state
Projects have no published_at. Creating one publishes it. Say so on the create button — "Add project" with the helper "Projects are visible on your public page as soon as they're added."
No restore endpoint
The asymmetry to design around. DELETE /api/projects/{id} soft-deletes but nothing brings it back. Until that changes, the UI must treat project deletion as permanent — see Gaps.
SLUG_ALREADY_EXISTS
409. Same handling as posts: suggest, don't discard.
J6

Build a résumé

The heaviest form in the product: five repeatable collections in one document.

  1. Start from role and identity
    Role, display name, bio, photo. Multiple CVs per person is the point — one tailored per audience — so name each by its role in the list.
    POST /api/cvs → 201 { id }
  2. Fill the five collections
    Core skills, education, experience, highlighted projects, contact details. Each is an add/remove/reorder list with the same row grammar, so learning one teaches the other four.
  3. Treat experience as the hard case
    A row carries company, position, location, dates, description, plus tasks[] and achievements[]. Collapse rows to a one-line summary by default and expand one at a time; ten expanded rows is not a form, it is a wall.
  4. Handle "current position"
    end_date is optional and absence means current. Render a "I currently work here" checkbox that clears the field, never a blank date input people have to intuit.
  5. Save deliberately
    Unlike the post editor, this form has an explicit Save. PATCH for a section edit; PUT only from a full-document editor that loaded every field.
    PATCH /api/cvs/{id} · PUT /api/cvs/{id}
  6. Share
    The public URL needs both username and CV id, so it is a copyable link rather than a guessable path. Show it as a read-only field with a copy button.
    GET /api/public/cvs/{username}/{cv_id}
Branches
CV_UNAUTHORIZED
403. Same treatment as a foreign post: a plain page, not a modal, with a way back.
Soft-deleted CV
Recoverable. CVs have restore. Deleting moves the card to an "Archived" filter on the list with a Restore action; only from there is a hard delete offered.
photo_url is a string
Not media-module backed. Accept a URL, and where an uploaded image is wanted, run J8 with attachment_target: Resume and paste the read URL — noted in Gaps as a seam.
J7

Curate topics

Keep one vocabulary across posts and projects, from inside the work rather than as a chore.

  1. Create where they are needed
    The topic combobox in either editor offers "Create «Rust»" when nothing matches. Most topics should be born this way; the management screen exists for tidying, not for setup.
    POST /api/topics { title, description }
  2. Require the description
    The API takes both fields. In the inline create, ask for a one-line description in the same popover — a taxonomy of bare words stops being useful at about fifteen entries.
  3. Review on one screen
    Title, description, and usage counts assembled client-side from the post and project topic endpoints. Sort by usage so the unused ones surface themselves.
    GET /api/topics
  4. Retire, don't rename
    Only soft delete exists. Name a topic well or replace it: create the new one, retag, retire the old. Frame the action as "Retire topic" so it reads as reversible-in-principle rather than destructive.
    DELETE /api/topics/{topic_id}
Branches
TOPIC_ALREADY_EXISTS
409. In the inline creator this is a near-miss, not a failure: "You already have a topic called Rust" and select it for them.
No update endpoint
A typo is unfixable. Validate hard at creation and preview the topic exactly as it will appear on the public page before committing.
Retiring a topic in use
Count it first. GET /api/topics/{id}/usage returns the real numbers, so the dialog can say "Retire «Rust»? It's on 6 posts and 2 projects." Never drop a topic off eight pages silently.
J8

Add an image

Local file → a variant URL on a public page. The only journey where the browser talks to something other than the API.

  1. Validate before asking for anything
    The server policy is 5 MB, 6000 px per side, JPEG/PNG/WebP. All three are checkable in the browser. Rejecting a 12 MB file locally is instant; the round trip is not.
  2. Request the upload URL
    Carries both file metadata and the attachment: target, target id, role, position, alt text, caption. Alt text is required by this plan, not by the API. It is no longer permanent — PATCH /api/media/{id} corrects it — but the picker is where someone is actually looking at the image, so it stays required there, and the media library gains an edit affordance.
    POST /api/media/upload-url → { upload_url, media_id }
  3. PUT the bytes to storage
    Direct to the signed URL. This is the only progress the UI can measure honestly, so the determinate bar belongs here and nowhere else.
  4. Show a pending tile immediately
    A tile in the grid with the local ObjectURL as its preview and a processing pill. The person continues working; the tile settles on its own.
  5. Poll, with a ceiling
    Every 2s, backing off to 5s, giving up at 60s with "Still processing — this one's taking a while" and a Check again button. An indefinite spinner is a lie about progress.
    GET /api/media/{media_id}
  6. Read through the right variant
    Request thumbnail for grids, small for cards, medium for in-body, large for covers. Never fetch large to render a 96 px tile. This signed route is the console path. Public pages use /api/public/media/{id}/{size} — a stable path that 302s to a freshly minted signature, so it is safe to render server-side and to cache.
    GET /api/media/{media_id}/{size} → { url, expires_at }
  7. Refresh URLs before they expire
    The response carries expires_at. Cache by media_id + size and re-request on expiry — a long-open editor showing broken images is the failure this prevents.
Branches
FILE_TOO_LARGE · INVALID_DIMENSIONS
400. Caught client-side first. If it still arrives, name the actual limit and the actual value: "That image is 8.4 MB. The limit is 5 MB."
MIME_EXTENSION_MISMATCH
400 — a .png that is really a JPEG. Never show the code. "This file's contents don't match its .png extension. Re-export it and try again."
MEDIA_FAILED
409 on read. Processing failed server-side. The tile turns failed with Retry (re-upload) and Remove. Failed tiles stay visible until dismissed — a silently vanishing upload is worse than a visible failure.
STORAGE_ERROR
502. Not the person's fault and not fixable by them. "Uploads are temporarily unavailable. Your post is saved — try the image again in a few minutes."
TARGET_NOT_FOUND
400. A client bug: uploading before the parent exists. Guaranteed away by creating the draft first (J4 step 1).
J9

Read in public

A visitor with a link. No session, no token, no idea any of the above exists.

  1. Land anywhere
    Every public route is server-rendered from the SvelteKit layer, so a shared link is a real page with real metadata — not a shell that fetches after paint.
    GET /api/public/blog/{username}/{slug}
  2. Browse across
    The three public listings — posts, projects, résumé — share a header keyed on the author, so any entry point leads to the other two.
    GET /api/public/blog/{username} · /api/public/projects/{username}
  3. Follow topics — the chips are real links
    Both public listings accept search, topic_id, sort, page and per_page, the same query struct the console uses. Render topic chips as links and paginate long archives; no backend work is needed for either.
    GET /api/public/blog/{username}?topic_id=&search=&page=&per_page=
  4. Never leak the console
    No edit affordances, no draft indicators, no "Sign in" nag over the content. The public reader is not a lapsed author.
Branches
POST_NOT_FOUND
404. Also what an unpublished or archived post returns. Show the author's other posts on the 404 rather than a bare dead end.
USER_NOT_FOUND
404 on the whole space. A generic not-found page. Never confirm which usernames exist.
Scheduled post, not yet due
404 until the timestamp passes. Expected, not an error — and the reason the console must show authors a clear "goes live in 3 days" state.
Images on public pages
Fixed. Public responses now carry media as a stable path that redirects to a signed URL — render it straight into src. One state to handle: variants can be empty while sizes are still generating, which is a pending tile rather than an error.
J10

Change or close the account

The smallest surface and the highest stakes. One editable field and one irreversible button.

  1. Show what is fixed and what is not
    Username and email are read-only with an explanation, not greyed inputs. Only full_name is editable, because only full_name is accepted.
    GET /api/users/me
  2. Save the display name
    Explicit Save; optimistic update with rollback on failure.
    PUT /api/users/me { full_name }
  3. Put closure behind its own door
    A "Danger zone" panel at the bottom, outlined in --st-danger, containing exactly one action.
  4. Make the consequence concrete before confirming
    List what goes dark, with counts: "12 posts, 4 projects and 2 résumés will stop being publicly reachable." Require typing the username to enable the button.
    DELETE /api/users/me
  5. Exit completely
    Clear tokens, clear the cookie, land on a plain confirmation page. Every later API call returns 403 USER_DELETED, which J2 already handles.
Branches
Soft delete, not erasure
The row survives. Do not promise deletion the backend does not perform. Say "Your account will be closed and your public pages taken down."
INVALID_FULL_NAME
400. Inline under the field, previous value retained.
No self-serve reactivation
There is no undelete endpoint. The confirmation must state that reopening requires contacting support, since the UI cannot offer it.

06

Interaction laws

Ten rules that hold on every screen. They are what makes the fifth screen someone opens feel like the first four, which is the whole of "predictable".

One primary action per screen

Exactly one amber button in view. Everything else is a bordered secondary or a plain text action. Two amber buttons means neither is the answer.

Destruction has three rungs

Archive — one click, undo toast for 8 seconds. Restore — one click, no confirm. Purge — a dialog naming the item, requiring the title to be typed, with a danger-coloured button. Never skip a rung, and never dress a purge as an archive.

PATCH is tri-state; the UI must be too

Omitted leaves a field alone, null clears it, a value sets it. So the editor tracks which fields the person actually touched and sends only those. Sending the whole object back means one editor's stale read silently reverts another tab's edit.

Lists share one control bar

Search left, filters centre, sort right, in that order, on posts, projects, CVs and media. Defaults are page=1, per_page=10, and each resource's own default sort. Search debounces at 300 ms and writes to the URL, so a filtered list is a shareable, reloadable, back-button-safe address.

Optimistic only when it is reversible

Renames, topic chips, reordering — apply immediately, roll back on failure. Publish, purge, upload, account closure — wait for the server. Optimism about an irreversible action is just an inaccurate screen.

Four states, always, for every collection

Loading — skeletons shaped like the rows, never a centred spinner. Empty — why it is empty and the one action that fixes it. Filtered-empty — distinct from empty, with a Clear filters button. Error — what failed and a Retry.

The save indicator is singular

Autosaving screens report state in one fixed place near the title. No toast per keystroke, no second indicator in a corner. Toasts are for things a person cannot see happen.

Never render a raw error code

Codes go to the console and to telemetry. The screen gets a sentence in the product's voice with a way forward. The mapping in Feedback is the whole contract — nothing reaches a person that is not in that table.

Ownership failures are pages, not modals

403 and 404 on a detail route mean the URL was wrong or the item is someone else's. That is a destination, not an interruption: render a page with an explanation and a route back to the list.

Keyboard and focus are not a phase two

Visible focus everywhere via the accent border already in the login form. Dialogs trap focus and restore it on close. Every destructive dialog opens with focus on Cancel, never on the button that destroys.

07

Feedback

The backend has 41 error codes across eight groups. People do not need 41 experiences — they need six, chosen by what they can do next. Classify first, then write the sentence.

Rate limits are a designed experience, not an exception

Five routes are limited and all five are ones a frustrated person hits repeatedly: login (10 per 5 min), register (5 per hour), password reset request (5 per hour), reset completion (10 per hour), refresh (30 per 5 min). Read Retry-After, disable submit, and count down visibly. A dead button with no explanation reads as a broken product at exactly the moment someone is already annoyed.

The refresh limit is the one that bites engineering rather than users: it is why J2 insists on a single queued refresh rather than one per in-flight request.

Where the API and the journeys don't meet

This section listed fourteen gaps. Backend round one shipped all fourteen, including the two both sides had written off. Four narrower gaps remain, none of which blocks a journey. What follows is the resolved list first, because several of the rules elsewhere in this document only made sense while those gaps existed.

Closed — and three of them reversed a rule in this document

Public media now ships as a stable path per variant that 302s to a signed URL, which also resolved the Markdown inline-image question for free. Resend verification, project restore, topic rename, slug availability, usage counts, batched media status, public author identity, bulk operations and shareable draft previews all exist. Blog search was case-sensitive and is not any more. Public listing filters turned out to have existed all along.

The three that changed this document: media metadata is patchable, so alt text is correctable rather than permanent; media has restore and hard delete, so it follows the same ladder as everything else; and topic usage counts exist, so destructive confirmations can state a real number instead of warning generically. J5, J7, J8, J9 and the state model have all been corrected.

The four that remain

photo_url still bypasses the media module

seam

A CV's photo is a plain string while attachment_target: "resume" exists in the media module — two ways to put an image on a résumé, only one of which gets resizing and variants. Note this is now inconsistent with the user avatar, which R5 made an ordinary media attachment. The pattern exists; the CV has not adopted it.

Media has no unfiltered list

seam

Listing is by-target only, so a combined media library means one call per target merged client-side. Workable, and it makes "everything I've uploaded" four requests with no paging.

No summary endpoint

later

The overview screen assembles its counts from the total field of three paginated lists fetched at per_page=1. Fine at this scale, worth replacing before it isn't.

Email and password cannot be changed while signed in

later

PUT /api/users/me now takes full_name and bio, and will take locale. It still does not take email or password, so a password change goes out through the forgot-password flow. J10 states the constraint rather than showing fields that do nothing.

Two open questions, not gaps

Whether position is patchable alongside alt_text — which decides whether project galleries get drag-to-reorder — and whether the public media route checks the owning post's publication state. Both are filed in the API Round Two document as C2 and C3.
